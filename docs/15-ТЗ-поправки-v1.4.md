## 1. Журнал изменений (вставить перед разделом 0)

**v1.4 (11.11.2026, по результатам архитектурной доработки `16` v0.2):**
1. Введён **LLM Gateway** как часть Model Router: единственный путь сторонних проектов к моделям (S4).

4. «Правило двух» (§6B.4-B) конкретизировано для профилей и режимов GUI-агента (S17).
5. Добавлены граница доверия Windows Companion, цепочка поставок навыков/MCP, правила визуального канала и HAR (S12, S17).
6. Добавлены угрозы T-13…T-18, антипаттерны AP-27…AP-31, неизвестные U-16…U-19, вопросы В-20…В-23, риски R-26…R-30.
7. Добавлены ворота академической добросовестности и инженерной ответственности для сценария диплома (S14).
8. Статусы возможностей внешних проектов: введён `claimed` (заявлено, не проверено).
9. Добавлен **раздел 6D «RAG для больших проектов»** и этап **S22** (индексация и поиск по корпусам, не помещающимся в контекст, например диплом): гибридный поиск на SQLite FTS5 + векторный слой, дешёвая локальная модель эмбеддингов, обязательные цитаты, классы данных, оценка на размеченном наборе вопросов.
10. Добавлен **Google Harness²** (рекурсивная обвязка агента) как референс для S21 и изолированный эксперимент S15; жёсткие ограничения: только proposal, sandbox/synthetic, через Gateway; ADR-M.
11. Добавлен **Obscura** (лёгкий read-only headless-браузер, Rust+CDP, Apache-2.0) как четвёртый уровень в лестнице выбора браузера S8; read-only режим `web-fetch-light`; ADR-N.

### 2.20. Новый раздел 6D «RAG для больших проектов» и этап S22 (вставить после §6C)

#### 6D.0. Назначение и принципы

Проекты вроде диплома (десятки документов, сотни страниц, главы текста, расчёты, чертежи) не помещаются в контекст модели. Нужен слой поиска, который по запросу достаёт **нужные фрагменты с источником**, а не пересказывает «по памяти».

1. **RAG — не замена структурным данным.** Для диплома основа — структура проекта: оглавление, таблица утверждений (`Claim`), `Evidence`, `CalculationRun`, реестр источников. RAG ищет только по неструктурному корпусу (тексты, PDF, заметки). Числа берутся из `CalculationRun`, а не из найденного текста.
2. **Retrieval — инструмент оркестратора** (just-in-time, ТЗ 15 §6B.4-C), а не долговременная память модели. Корпус проекта ≠ память L2–L4 (§6A.5): из корпуса в память ничего не пишется автоматически.
3. **Найденное — недоверенные данные.** Фрагмент внешнего происхождения несёт метку `trust=untrusted` и не может менять план, политики или права (ТЗ 15 §6A.1).
4. **Класс данных сохраняется на всех уровнях:** чанк, эмбеддинг, индекс, кэш, результат поиска. Эмбеддинг считается данными того же класса, что исходный текст.
5. **Дёшево по умолчанию:** сначала лексический поиск (SQLite FTS5), векторный слой добавляется по измеренной пользе; эмбеддинги — **локальной малой моделью** на CPU, без платных API; вызовы LLM при индексации — только где нужно, пакетно, через дешёвый профиль (`deepseek-flash` или иной из `14`) в непиковые часы (§6C П-10).
6. **Воспроизводимость:** версия индекса = хеши корпуса + версия чанкера + модель эмбеддингов + параметры. Ответ ссылается на версию индекса.
7. **Нет постоянного векторного сервера.** Единая БД SQLite (ТЗ 15 §4.1, §5.1); внешние векторные СУБД не вводятся без ADR и метрик.

#### 6D.1. Корпуса и уровни индекса

| Уровень | Что индексируется | Назначение |
|---|---|---|
| L-A карта документа | Оглавление, краткое резюме документа/главы (LLM, пакетно) | Выбор нужного документа и раздела |
| L-B раздел | Текст раздела целиком (родительский блок) | Расширение контекста вокруг найденного |
| L-C чанк | Фрагмент 1–N абзацев | Основной поиск |
| L-D сущности | Таблицы, формулы, рисунки, подписи, список обозначений | Точный поиск структурных объектов; числовые значения — ссылкой на источник/`CalculationRun` |

Корпуса диплома (отдельные индексы, раздельные права): `methodology` (методичка кафедры — наивысший приоритет), `standards` (нормативы), `literature` (источники из Zotero), `source-projects` (извлечённое из PDF/DWG/таблиц), `thesis-text` (текст ВКР по главам и версиям), `notes` (заметки vault). Корпуса с внешним контентом и собственные документы владельца не смешиваются в одном запросе без разрешения (§6D.8).

#### 6D.2. Приём и разбиение на чанки

1. Вход — `ParsedDocument` из S11 (страницы, блоки, bbox, уверенность). Индексировать только то, что распознано; пропуски и низкая уверенность записываются как метаданные, а не «додумываются».
2. Границы чанков по структуре (раздел → абзац → предложение), не по фиксированному числу символов. **Размер чанка и перекрытие не фиксируются в ТЗ:** подбираются экспериментом (§6D.10), значения записываются в ADR.
3. Схема «родитель–ребёнок»: поиск по малым чанкам, выдача с расширением до родительского раздела в пределах токенного бюджета.
4. Таблицы, формулы и рисунки — отдельные чанки с ссылкой на страницу/bbox; числа в таблицах не «пересказываются» моделью.
5. Метаданные каждого чанка: `chunk_id`, `doc_id`, `source_ref` (Zotero/путь), `page`, `bbox`, `section_path`, `doc_version`, `index_version`, `data_class`, `trust`, `lang`, `stale`, `parser`, `confidence`, `content_hash`.
6. Русский язык: токенизация FTS5 по умолчанию не делает морфологического разбора. Проверить варианты (нормализация/лемматизация, триграммный токенизатор FTS5, словарь обозначений и сокращений) и выбрать по метрике (U-21).
7. Глоссарий терминов и обозначений проекта хранится как структурный список и используется для расширения запросов.

#### 6D.3. Модель эмбеддингов (требования; выбор — по измерению)

Требования: многоязычная с хорошим русским; работает на CPU ноутбука без GPU; помещается в ограничение RAM рядом с остальным комплексом (классы L/M/H/X, `16` §6); лицензия MIT/Apache-2.0/BSD (ТЗ 15 В-14); известная размерность вектора; стабильная версия.

Кандидаты **для проверки** (не рекомендация; наличие, лицензию и качество на русском проверить в S0B/S22): малые многоязычные семейства E5, BGE-M3, Qwen3-Embedding малых размеров. Внешние embedding-API провайдеров допускаются только для классов данных, разрешённых Policy (по умолчанию — `public`), с проверкой цены и условий обработки данных (U-22).

Правила:
- Эмбеддинги вызываются **через LLM Gateway** (эндпоинт embeddings): единый учёт, бюджет, класс данных; локальная модель за тем же интерфейсом.
- Для `LOCAL_ONLY` и `secret` — только локальная модель.
- Смена модели или её версии = **полная переиндексация** и новая версия индекса; смешивать векторы разных моделей в одном индексе запрещено.
- Кэш эмбеддингов запросов и чанков по `content_hash`, чтобы не пересчитывать неизменное.
- Выбор модели — ADR-K по протоколу §6D.10 (качество на русском golden-set, секунд на 1000 чанков, пик RAM, размер индекса).

#### 6D.4. Хранилище и индексы

- Единая SQLite-БД проекта (WAL): таблицы `rag_documents`, `rag_chunks`, `rag_chunks_fts` (FTS5), `rag_vectors`, `rag_index_versions`, `rag_runs` (запросы и результаты для аудита, без лишних тел приватных данных).
- Векторный слой: кандидаты — расширение SQLite для векторов, точный перебор в памяти для небольших корпусов, лёгкая библиотека приближённого поиска в процессе. Для корпуса уровня диплома точный перебор может быть достаточен: **решение по измерению** (ADR-K), не по предположению. Доступность расширений в выбранной сборке SQLite/Python проверяется в S0 (U-21).
- Индексы по классам данных хранятся **раздельно** (отдельные файлы/схемы); смешанный индекс запрещён.
- Бэкап индексов входит в S16; индекс восстанавливаем из корпуса, потеря индекса — переиндексация, не потеря данных.

#### 6D.5. Конвейер поиска

1. **Разбор запроса:** правила + (при необходимости) дешёвая LLM для переписывания/разложения многошагового вопроса; расширение глоссарием.
2. **Фильтры до поиска:** `data_class` ≤ допустимого для профиля, корпус из разрешённых профилю, `stale=false` (или явный флаг), версия документа.
3. **Гибридный поиск:** BM25 (FTS5) + векторный; слияние Reciprocal Rank Fusion; веса — по метрике.
4. **Реранкер** (малая локальная модель) — только если докажет прирост метрик на golden-set при допустимой задержке и RAM (ADR-L).
5. **Расширение:** до родительского раздела и соседних чанков в пределах токенного бюджета; дедупликация.
6. **Выдача:** список `{chunk_id, text, source_ref, page, bbox, section_path, score, trust, data_class, doc_version, index_version, stale}`.
7. **Режим «нет ответа»:** если лучший результат ниже порога или фильтр оставил пусто — явный `no_evidence`, а не «лучшая догадка».

Инструменты для агентов (через Tool Registry, права по профилю): `rag.search`, `rag.get_chunk`, `rag.get_section`, `rag.get_outline`, `rag.find_claim_evidence`, `rag.list_sources`. Ограничения: число вызовов и токенов на шаг задаёт манифест; агентный цикл поиска без лимита запрещён.

#### 6D.6. Профиль RAG для диплома `[ДИПЛОМ +]`

1. **Цитирование:** каждая цитата/утверждение, опирающееся на корпус, проверяется кодом — фрагмент найден в исходном тексте страницы (дословно или по допустимой нормализации), `Claim → Evidence(page/bbox/source)`. Совпадение «по смыслу» не засчитывается.
2. **Числа:** только из `CalculationRun` или из первичного источника с page/bbox; число, взятое из текста чанка, помечается `unverified_number` (AP-02, AP-36).
3. **Сквозные вопросы** («согласованность терминов по всей записке», «где упоминается допущение X») — map-reduce read-only субагентами по главам с краткими структурированными резюме; редьюс выполняет лид/оркестратор.
4. **Иерархические резюме** глав и документов обновляются инкрементально и помечаются `stale`, если исходный текст или расчёт изменился.
5. **Методичка кафедры** — отдельный корпус с наивысшим приоритетом; правила из неё извлекаются в структурные записи (`ThesisRequirementsParser`) и **не** ищутся только эмбеддингами.
6. **Связь с памятью:** устойчивые решения владельца (структура, допущения) — в память/`decision_log`, а не в RAG-корпус.

#### 6D.7. Инкрементальное обновление

- Обнаружение изменений по `content_hash` документа/страницы; переиндексация только изменённого; удаление исчезнувших; версии индекса.
- Каскад `stale`: изменился расчёт, источник или глава → связанные резюме, чанки зависимых сущностей и фрагменты DOCX помечаются и ставятся на повторную проверку (расширяет §10.3 `16`).
- Построение индекса — job класса H (одновременно один), с бюджетом и временем; пакетные LLM-резюме — в непиковые часы.
- Журнал индексации: что добавлено/обновлено/пропущено и почему.

#### 6D.8. Безопасность RAG

| Угроза | Мера |
|---|---|
| T-19 Prompt injection внутри индексируемых документов (PDF, веб-источники, комментарии) | Фрагменты — `untrusted`; извлечение полей через `quarantine-reader` (AG-00); инструкции из текста не исполняются; red-team кейсы в корпусе (S17-T6) |
| T-20 Отравление корпуса (подмена файла, подложный источник) | Хеши, provenance, карантин новых внешних документов, ревью перед включением в `methodology`/`standards` |
| T-21 Утечка через эмбеддинги/кэш/индекс | Класс данных на каждом уровне, раздельные индексы, шифрование бэкапов, локальные эмбеддинги для `LOCAL_ONLY` |
| T-22 Смешение классов данных в одном запросе | Фильтры до поиска; запрос к нескольким корпусам разных классов — только с разрешением Policy |

**Правило двух:** профиль, ищущий в корпусе с внешним содержимым (веб-источники), получает свойство A; одновременно с B и C он запрещён. Режимы `web-mode`/`corpus-mode` из `16` §2.2 применяются и к retrieval: внешние тексты попадают к писателю только как типизированные значения через AG-00.

#### 6D.9. Стоимость и ресурсы

- По умолчанию стоимость запроса = локальная CPU-нагрузка; платных вызовов нет. Платные вызовы (резюме, переписывание запроса) идут через Gateway по бюджету задачи; при исчерпании — `blocked_budget`.
- Метрики, обязательные в отчёте: `$ на 1000 чанков`, `секунд на 1000 чанков`, пик RAM при построении и при поиске, размер индекса на диске, p50/p95 задержки поиска (измерить, не обещать).
- Индексация и поиск учитываются классами ресурсов `16` §6; построение индекса не совмещается с классом X.

#### 6D.10. Оценка качества (golden-set) и выбор конфигурации

1. **Набор вопросов:** ≥ 50 размеченных вопросов по реальному/обезличенному корпусу диплома с эталонными `doc/page`: фактические, многошаговые, по таблицам, по формулам/обозначениям, «ответа в корпусе нет». Разметку делает владелец или проверяет им выборочно.
2. **Метрики:** `recall@k`, `MRR`, `nDCG`, `citation precision` (цитата реально подтверждает утверждение), `groundedness`, доля корректных `no_evidence` на вопросах без ответа, задержка, стоимость, RAM.
3. **Сравниваемые конфигурации:** (A) только FTS5; (B) только вектор; (C) гибрид; (D) гибрид + реранкер; (E) гибрид + иерархические резюме. Повторяемость — `pass^k` (ТЗ 15 §6B.5, S15-AC-5).
4. **Критерий приёмки конфигурации:** выбирается минимально сложная конфигурация, дающая целевые метрики; пороги recall/precision утверждает владелец после первого прогона, а не задаются заранее. Усложнение (вектор, реранкер, резюме) принимается только при измеренном приросте.
5. LLM-судья для groundedness допускается с отчётом калибровки (S15-AC-6).

#### 6D.11. Интеграция с Context Builder и оркестратором

- Context Builder (§6A.5.2, §6B.4-C) получает результаты как ссылки + фрагменты по токенному бюджету; метки `trust`/`data_class`/`index_version` сохраняются; суммаризация результатов поиска не «отмывает» недоверенность.
- Когда читать документ целиком, а когда использовать retrieval — порог по размеру/типу задачи определяется экспериментом и записывается в конфиг маршрутизации.
- Рецитация цели и `NOTES.md` по задаче ведутся независимо от RAG.

#### 6D.13. Этап S22. RAG: индексация и поиск

**Зависит от:** S3, S4 (Gateway, embeddings), S11, S17, S21 (Context Builder, FTS5). **Оценка:** 6–9 агент-дней. **Приоритет:** P1. **Дорожная карта:** фаза C (`16` §8.2).

**Задачи**
1. S22-T1. Схема БД и миграции RAG (§6D.4); раздельные индексы по классам данных.
2. S22-T2. Приём `ParsedDocument` → чанкер (структурный, родитель–ребёнок), метаданные, хеши, инкрементальное обновление и каскад `stale`.
3. S22-T3. Эндпоинт embeddings в LLM Gateway; локальная модель за тем же интерфейсом; кэш по `content_hash`; запрет смешения моделей в индексе.
4. S22-T4. Лексический слой (FTS5) с вариантами обработки русского (U-21) и словарём обозначений.
5. S22-T5. Векторный слой (ADR-K) и гибридное слияние (RRF); опциональный реранкер (ADR-L).
6. S22-T6. Инструменты `rag.*` для Tool Registry с лимитами и правами по профилям; режим `no_evidence`.
7. S22-T7. Иерархические резюме (пакетно, дешёвая модель, непиковые часы) с пометкой `stale`.
8. S22-T8. Проверка цитат кодом (точное вхождение в исходный текст страницы); связь с `Claim/Evidence`.
9. S22-T9. Golden-set (≥ 50 вопросов), раннер метрик, сравнение конфигураций A–E, отчёт стоимости и ресурсов.
10. S22-T10. Интеграция с Context Builder, портал (просмотр корпусов, версий индекса, `stale`, результатов поиска, метрик).
11. S22-T11. Red-team корпуса: инъекции в документах, подмена источника, попытка смешения классов данных.

**Критерии приёмки**
- S22-AC-1: индекс воспроизводим — повторная сборка на тех же входах даёт тот же `index_version` и идентичные результаты поиска на golden-set.
- S22-AC-2: изменение одного документа приводит к переиндексации только его чанков; связанные резюме и зависимые сущности получают `stale` (тест на 20 изменений).
- S22-AC-3: запрос профиля с классом данных ниже требуемого не возвращает чанки более высокого класса; `LOCAL_ONLY` не уходит ни в один внешний вызов, включая эмбеддинги и резюме (перехватчик сети в sim).
- S22-AC-4: смешение разных моделей эмбеддингов в одном индексе технически невозможно (тест).
- S22-AC-5: golden-set ≥ 50 вопросов прогнан по конфигурациям A–E; отчёт содержит `recall@k`, `MRR`, `citation precision`, долю корректных `no_evidence`, стоимость, задержку, RAM; выбранная конфигурация обоснована ADR.
- S22-AC-6: ответ без ссылки на чанк/страницу не принимается Quality Gate (AP-32); цитата, не найденная в исходнике, блокируется (AP-33) — не менее 20 негативных тестов.
- S22-AC-7: red-team корпуса (≥ 20 кейсов инъекций и подмен): ни один не приводит к внешнему эффекту, изменению политик или записи в память.
- S22-AC-8: числа в тестовых ответах берутся из `CalculationRun` либо помечены `unverified_number`; число из текста чанка не проходит в финальный документ (AP-36).
- S22-AC-9: замеры `$ на 1000 чанков`, `секунд на 1000 чанков`, пик RAM, размер индекса записаны в `reports/resource-profile.md`; построение индекса не совмещается с классом X.
- S22-AC-10: при удалении документа владельцем его чанки, эмбеддинги, кэш и резюме удаляются, в поиске не появляются.

#### 6D.14. Дополнения к реестрам

- **Неизвестные:** U-20 — скорость и RAM кандидатов эмбеддингов на CPU ноутбука, качество на русском техническом тексте; U-21 — версии SQLite/Python, доступность FTS5 (в т.ч. триграммного токенизатора) и векторного расширения; U-22 — наличие и цена embedding-API провайдеров, условия обработки данных (только для `public`).
- **Вопросы владельцу:** В-24 — допустимы ли внешние embedding-API для `private` (по умолчанию нет); В-25 — объём корпуса диплома (число документов, страниц, размер) для планирования; В-26 — бюджет на LLM-резюме при индексации и согласие на пакетную работу в непиковые часы.
- **Риски:** R-31 — низкое качество поиска на русском техническом тексте (формулы, обозначения, таблицы); R-32 — рост индекса и RAM; R-33 — ложная уверенность из-за «похожих» чанков и устаревших резюме.
- **Угрозы:** T-19…T-22 (§6D.8).
- **ADR:** K — модель эмбеддингов и векторный слой; L — реранкер, размер чанков, токенизация русского.
- **Матрица трассируемости:** «v1.4: RAG для больших проектов» → S22 → S22-AC-1…10; связь с S3, S4, S11, S17, S21.
- **§6A.5 (память):** уточнение — корпус проекта (RAG) и память L2–L4 разделены; запись из корпуса в память только через очередь ревью.
